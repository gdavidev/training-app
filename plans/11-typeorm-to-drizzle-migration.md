# TypeORM to Drizzle ORM Migration

**Priority:** Architecture Improvement  
**Date:** 06/05/2026

## Why Drizzle fits better

- First-class `expo-sqlite` integration (`drizzle-orm/expo-sqlite`)
- Schema as plain TypeScript objects — no decorators, no `reflect-metadata`, no babel plugins
- `drizzle-kit generate` runs in Node.js and produces plain `.sql` files you can review before committing
- `useMigrations()` hook handles in-app migration execution — replaces `AppDataSource.initialize()`
- ~40% smaller bundle than TypeORM

## What stays the same

- SQLite database file name (`davi-training.db`) and all table/column names — no data migration needed on existing devices
- All 8 `hooks/query/` files retain the same exported function signatures
- `@tanstack/react-query` usage is unchanged

## Schema shape

**TypeORM (current):**
```typescript
@Entity("exercise")
export class Exercise {
  @PrimaryGeneratedColumn() id: number;
  @Column({ default: "" }) sets: string;
  @ManyToMany(() => Muscle, { eager: true })
  @JoinTable()
  muscles: Relation<Muscle[]>;
}
```

**Drizzle (new):**
```typescript
export const exercise = sqliteTable("exercise", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  sets: text("sets").notNull().default(""),
});
export const exerciseMuscles = sqliteTable("exercise_muscles_muscle", {
  exerciseId: integer("exerciseId").notNull().references(() => exercise.id, { onDelete: "cascade" }),
  muscleId: integer("muscleId").notNull().references(() => muscle.id, { onDelete: "cascade" }),
});
export const exerciseRelations = relations(exercise, ({ many }) => ({
  muscles: many(exerciseMuscles),
}));
```

## Query API mapping

| TypeORM | Drizzle |
|---|---|
| `repo().find({ where: { id }, relations: { muscles: true } })` | `db.query.exercise.findMany({ with: { muscles: { with: { muscle: true } } } })` |
| `repo().save(repo().create(data))` | `db.insert(table).values(data).returning()` |
| `repo().update(id, data)` | `db.update(table).set(data).where(eq(table.id, id))` |
| `repo().delete(id)` | `db.delete(table).where(eq(table.id, id))` |
| `repo().clear()` | `db.delete(table)` |
| `repo().remove(entities)` | `db.delete(table).where(inArray(table.id, ids))` |

## Trickiest parts

- **M2M (exercise ↔ muscle):** `exercise_muscles_muscle` junction table must be defined explicitly in schema; relation queries need two `with` hops
- **`useLastWeightsMap`:** filters across a join (`where: { execution: { isCompleted: true } }`) — becomes a Drizzle `innerJoin` or relational query with `where` on the joined table
- **`savePresetItems` in `usePreset`:** bulk delete + re-insert pattern — maps directly to `db.delete().where()` + `db.insert().values([])`

## Migration strategy for existing devices

The `drizzle/` SQL files will use the same DDL as the existing migrations (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ADD COLUMN` with PRAGMA guard) so Drizzle's migration runner treats them as a no-op on already-initialized devices.
